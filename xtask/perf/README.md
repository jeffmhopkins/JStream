# The perf suite

`cargo xtask perf` loads the engine with stress scenes and reads where the time and the
memory go, so a regression in drawing cost, a leak or a scene that stops drawing shows up
as a number, not as a stream that stutters. It reads the engine through
[`profile.get`](../../docs/adr/0103-per-item-performance-profile.md) and the daemon's
process, and needs no hardware: on Linux it runs on lavapipe, Mesa's software Vulkan.
It is the repository's copy of the harness behind #1140's first results.

It is not a release gate on real hardware. `jstream bench`
([jstream-cli › Usage](../../apps/jstream-cli/README.md#usage)) runs a standard load
through outputs and judges it against the alpha.5 bar. The perf suite measures many
small scenes one at a time, to say which kind of work costs what.

<a id="runner"></a>
## The runner
<!-- @section
covers = ["xtask/src/perf/**"]
-->

```sh
cargo xtask perf --openh264 ~/libopenh264-2.6.0-linux64.8.so          # every scene
cargo xtask perf --scene 'vf_*' --seconds 10 --no-build                # some of them
cargo xtask perf --check                                               # judge the run
cargo xtask perf --list                                                # what there is
```

It builds `jstream-daemon` and `jstream-cli` (release, unless `--debug`; `--no-build`
uses what is built), then:

1. Starts the daemon on a free port with everything it writes under
   `target/perf/run/`, which each run clears: the token, the collection file, the logs,
   the effect and plugin folders, and on Linux its data folder (`XDG_DATA_HOME`). On
   Linux without `VK_DRIVER_FILES` it points Vulkan at lavapipe when Mesa's manifest is
   installed, as `cargo xtask e2e-stream` does. It writes the scenes' files there too
   (a 1080p still, a mask, an animated GIF, a 3D LUT and two HTML pages), generated by
   the runner so the repository holds no media.
2. Talks to it through `jstream-cli mcp`, the stdio MCP proxy, so xtask needs no client
   of its own: it writes and reads JSON lines.
3. Sets the canvas (`--canvas`, 1280×720 unless given), builds the base scene (one
   colour) and records the program to `program.mp4`. The program stage draws only
   while something takes its frames, so without the recording `profile.get` would
   report no drawer. On Linux without VA-API that needs Cisco's OpenH264:
   `--openh264 <library>` puts a copy of the pinned release (the file the app
   downloads, unpacked) where the daemon looks for it, and the daemon checks it against
   its pin. Without an encoder the run stops and says so.
4. Measures the base scene, then each scene in turn: builds it in `batch` calls, cuts
   to it, waits `--settle` seconds (3) and a full window (`--seconds`, 5), so the window
   never reaches back before the cut, reads `profile.get` over that window and the
   process, cuts back and deletes what it made through `delete.plan`. A scene that
   fails is reported as an error row, and the run goes on from a clean engine. A churn
   scene (`cycles`) is built, shown for 2 seconds, left and deleted that many times,
   and then measured on the base scene. Last, it measures the base scene again.
5. Prints a table, one row a scene, and writes every row with its full profile to
   `target/perf/report.json` (`--out` for elsewhere). The columns: the program's frames
   a second over the window, its mean and worst frame time, frames over budget and
   skipped, plans, process CPU, and from `/proc` (Linux only) the daemon's resident MB,
   threads, open handles and child processes.

`--browser` adds the scenes that need the browser helper, which must then be where the
daemon finds it ([ADR-0095](../../docs/adr/0095-browser-helper-on-linux.md)); without
it they are listed as skipped. `--scene` takes a name, or a prefix ending in `*`, and
may be repeated.

`--bench <gates.json>` also runs `jstream bench --scenario all --preset cut` against the
same daemon once the scenes are measured and `report.json` is written, writing to `target/perf/run/bench/`, and judges
it against that gates file. A failing bench fails the run as `--check` does. The
`perf-linux` job in `.github/workflows/bench.yml` runs the suite this way on lavapipe, on
`main` and on demand: `--check` with `xtask/perf/bench/gates-lavapipe.json`.

<a id="scenes"></a>
## Scenes
<!-- @section
covers = ["xtask/perf/*.json"]
-->

Each `*.json` file here holds one scene or an array of them, run in file-name order.
They use built-in kinds only, so any machine can build them, and each is
self-contained: the runner deletes what one made before the next starts. A scene is
`{"name", "about", "edits", "needs"?, "cycles"?}`. The runner creates the scene `name`
itself; `edits` are `batch` edits, and an entry
`{"each": {"count", "cols"?, "cycle"?}, "edits": [...]}` repeats its edits once per
index. Inside the edits, `{i}` in a string is the index and `"$i"` the index as a
number; `"$cell"` is the geometry of cell `i` of a `count`-cell grid `cols` wide (the
square root of `count`, rounded up, unless given) over the canvas, and `"$canvas"` the
whole canvas, and as object keys (`{"$cell": 1, "turn_deg": 30}`,
`{"$canvas": 0.8}` for 80% about the centre) they take the object's other keys;
`"$asset:<file>"` is one of the generated files; `"$<name>"` is entry `i`, wrapping,
of the block's `cycle.<name>` list. Any other string starting with `$` fails at load,
and `cargo test -p xtask` loads every shipped scene.

The scenes, by file: sources (200 colours, one shape placed 200 times, 100 texts, 50
1080p images, an animated GIF placed 20 times, 20 timers, 8 scopes, a backdrop, a chat
message), nesting (six scenes deep, one group placed 16 times), 3D (24 tilted shapes,
12 placements with their own perspective, 12 models), browser pages (one, and six),
filters (each of the 18 video filters on one 1080p still, 30 items with item effects, a
scene's own chain) and churn (a busy scene made, shown and deleted 12 times).

<a id="thresholds"></a>
## Thresholds
<!-- @section
covers = ["xtask/perf/thresholds.toml"]
-->

`--check` judges the run against `thresholds.toml` (`--thresholds` for another file)
and exits non-zero when a row breaks a limit or a scene didn't run, naming each:

- `[default]`, and `[scene.<name>]` on top of it: `min_fps`, the program's frames a
  second over the window; `max_frame_ms`, its mean frame time; `max_over_budget_pct`,
  the share of its frames over budget.
- `[leak]`: `max_rss_growth_mb`, `max_thread_growth` and `max_handle_growth` across a
  churn scene, from after its first cycle to after its last; threads and handles also
  across the run, from the first base row to the last. Resident memory isn't judged
  across the run, because the allocator keeps what a heavy scene used.

The shipped limits are software-rendering bars for the `perf-linux` job: lavapipe on a
4-CPU GitHub-hosted runner with the OpenH264 recording. They are loose enough for the
spread between hosted runs (a scene's mean frame time has moved by up to 3x), and tight
enough that a scene that stops drawing, a several-fold regression or a leak fails. So
they judge each scene by its frame rate and mean frame time, and leave the share of
frames over budget at 100%, because that share flips for any scene drawing near the
33 ms budget. The base scene has a tighter frame-time bar, so a regression in a frame's
fixed cost shows there first. The scenes that software rendering makes slow (a 1080p
blur, glow, shadow, outline, sharpen, key or scroll, the models, many item effects, a
scene chain) have their own looser limits. An unknown key fails, so a typo can't turn
a limit off.

`bench/gates-lavapipe.json` holds the `--bench` gates for the same runner: the bench's
alpha.5 counters with room for software rendering, at least a fifth of the target frame
rate and no budget on frames over time, and quality-probe floors of 30 dB luma PSNR and
0.90 SSIM for Cisco's OpenH264 at software rates
([ADR-0145](../../docs/adr/0145-the-quality-probe-reads-back-the-compositor.md)). It sits in a folder of its own because every
`*.json` beside this file is read as a scene.
